## Описание проекта

Веб-приложение на Django для управления рассылками сообщений для клиентов. Приложение включает функциональность для создания, просмотра, редактирования и удаления рассылок, а также отправки сообщений по требованию.

**Курсовая работа состоит из двух частей:**
1. **Часть 1**: Разработка сервиса (базовая функциональность)
2. **Часть 2**: Расширение функциональности (аутентификация, права доступа, кеширование)

---

## ЧАСТЬ 1. Разработка сервиса

### 1. Управление клиентами

Реализовать CRUD-операции для получателей рассылки (клиентов).

**Модель «Получатель рассылки»:**
- `email` (строка, уникальное)
- `full_name` (Ф.И.О., строка)
- `comment` (комментарий, текст)

---

### 2. Управление сообщениями

Реализовать CRUD-операции для сообщений.

**Модель «Сообщение»:**
- `subject` (тема письма, строка)
- `body` (тело письма, текст)

---

### 3. Управление рассылками

Реализовать CRUD-операции для рассылок.

**Модель «Рассылка»:**

| Поле | Тип | Описание | Обязательное |
|------|-----|----------|--------------|
| `start_time` | datetime | Дата и время начала отправки | ✓ |
| `end_time` | datetime | Дата и время окончания отправки | ✓ |
| `status` | string | Статус рассылки (вычисляется динамически) | - |
| `message` | ForeignKey | Внешний ключ на модель «Сообщение» | ✓ |
| `recipients` | ManyToMany | Связь с моделью «Получатель» | ✓ |

**Статусы рассылки:**
- `'Создана'` — текущая дата раньше `start_time`
- `'Запущена'` — текущая дата между `start_time` и `end_time` (включительно)
- `'Завершена'` — текущая дата позже `end_time`

> **Рекомендация:** Вычислять статус динамически при каждом обращении к рассылке через метод `update_status()`.

**Пример реализации динамического статуса:**
```python
def get_object(self, queryset=None):
    obj = super().get_object(queryset)
    obj.update_status()  # Пересчёт и сохранение статуса
    return obj
```

**Валидация:**
- `start_time` не может быть в прошлом
- `start_time` должен быть раньше `end_time`

---

### 4. Отправка сообщений по требованию

Реализовать возможность вручную запускать рассылку через интерфейс пользователя и/или командную строку.

**Логика работы отправки:**

1. **Инициация**: Проверка временного окна
   - Если текущее время между `start_time` и `end_time` → отправка разрешена
   - Иначе → выдаётся сообщение об ошибке

2. **Определение получателей**: Выбираются все клиенты, связанные с рассылкой

3. **Отправка писем**: Для каждого клиента:
   - Выполняется отправка письма с помощью `send_mail()`
   - При успехе: создается запись о попытке со статусом `'Успешно'`
   - При ошибке: создается запись со статусом `'Не успешно'` и текстом ошибки

---

### 5. Попытки рассылок

Для каждой попытки отправки сообщения необходимо сохранять информацию.

**Модель «Попытка рассылки»:**
- `attempt_time` (дата и время попытки, datetime)
- `status` (статус: `'Успешно'` или `'Не успешно'`)
- `server_response` (ответ почтового сервера, текст)
- `mailing` (внешний ключ на модель «Рассылка»)

**Зачем хранить историю попыток:**
- Отслеживание эффективности рассылок
- Формирование статистики для пользователя
- Диагностика ошибок доставки писем

---

### 6. Главная страница

Отобразить на главной странице следующие показатели:

- **Общее количество** всех созданных рассылок
- **Количество активных рассылок** — у которых:
  - Текущая дата находится между `start_time` и `end_time`
  - Статус равен `'Запущена'`

  ```
  Время: [--Прошлое--] [start_time]===РАБОТА===[end_time] [--Будущее--]
  ```

- **Количество уникальных получателей** (общее число клиентов в системе)

## ЧАСТЬ 2. Расширение функциональности

### 7. Регистрация и аутентификация пользователей

Реализовать систему регистрации и аутентификации пользователей.

**Требования:**
- Регистрация на сайте с подтверждением email
- Вход и выход из системы
- Восстановление пароля

**Модель пользователя:**
- Наследуется от `AbstractUser`
- Дополнительные поля:
  - `email` (авторизация по email)
  - `avatar` (аватар)
  - `phone_number` (номер телефона)
  - `country` (страна)
- В настройках проекта заменить `AUTH_USER_MODEL` на текущую созданную модель

### 9. Ограничение доступа

**Общие правила:**
- Пользователи могут управлять только своими рассылками и клиентами
- Менеджеры могут просматривать все рассылки и клиентов, но не могут редактировать или удалять чужие данные

#### Роли и права доступа

**Пользователь:**
- ✅ Создание, просмотр, редактирование и удаление своих клиентов и рассылок
- ✅ Просмотр статистики по своим рассылкам

**Менеджер:**
- ✅ Просмотр всех клиентов и рассылок
- ✅ Просмотр списка пользователей сервиса
- ✅ Блокировка пользователей сервиса
- ✅ Отключение рассылок
- ❌ Редактирование/удаление чужих данных

**Реализация:**
- Добавить в модели (рассылки, сообщения, получатели) поле `owner` (владелец)
- В контроллерах создания переопределить метод `form_valid()`, чтобы прописывать текущего пользователя в `owner`
- В контроллерах переопределить QuerySet'ы для фильтрации по владельцам
- Реализовать проверки в шаблонах для ограничения доступа
- Создать группу «Менеджеры» с соответствующими правами в Meta классе моделей
- Создать команду для наполнения базы данных группой «Менеджеры»
